4. The product: Karkhana Voice (v3)

"The ERP you never open, because it calls you." (working title)

Submission description (197/200 chars, verified by count): Karkhana Voice: a voice-first control tower for small factories. It calls floor managers to confirm stock in Hinglish, watches supplier risk, warns before parts run out, dispatches breakdown calls.

4.1 Problem

Small manufacturers run on paper, Excel and WhatsApp because floor managers and store keepers won't type into Odoo/SAP. Stock data is late or wrong, shortages are found when a machine is idle, supplier dates are believed until they fail, money sits in over-ordered parts, breakdowns travel by shouting, shift knowledge lives in one head.

4.4 Core flows

Close: reconcile by exception (the one flow that must work)

Backend builds the expected-today list: POs due today + planned output from work orders and BOM.
Agent says it is an AI and the call is recorded; reads at most 5 items, ranked by Watchtower score; rest roll to next call.
Per item: "haan" confirms expected value; "nahi, 150 aaye" triggers an entry.
Each entry calls validate_entry (Section 5) before the read-back.
Output: "Pump-X kitne bane?" then backflush read-back through the BOM.
Scrap/extras: max 2 re-asks, then offer a human.
Supervisors only: three handover prompts (machine at risk, pending order, safety/quality issue).
Final read-back of anything that changed; goodbye.
Nothing is confirmed until the caller says yes to the read-back and validation passed. Day 1 for a new customer = opening count of the top 5 parts.

Open: reads top 3 ranked risks (part, shortfall/slip, date that matters, yes/no ask). "Haan" stores an approval (a record, not a purchase). Owner may add one spoken note ("Shree Fasteners ka truck strike mein phasa hai") stored as a signal for that supplier. Incoming supervisors hear max 3 handover items and ack each.

Alert, breakdown dispatch:

"Machine down" button names a machine.
Agent calls technician for ack + ETA.
If terminal status is no-answer, busy, failed, or call completes without a clear ack, orchestrator calls the supervisor next per the escalation matrix.
Timers stored in DB and polled (restart-safe). Demo: 60-90 s; production default: 10 min.
Metric: minutes from report to ack. 3+ incidents on a machine in 7 days feeds the Watchtower.
Alert, supplier ETA (Tier 2, consenting suppliers only): confirms a delivery date for an existing order. No price talk, no negotiation, no new orders. Updates the PO and triggers rescoring. If no real consenting supplier by Oct 30, role-play with a teammate and label it "simulated supplier".

5. Live validation via Bolna custom functions

Per the v3 plan: Bolna custom functions follow OpenAI function-calling spec and call any HTTP endpoint (key: "custom_task", value with method, url, param, optional api_token, headers). Parameter specifiers: %(name)s string, %(name)i integer, %(name)f float. The agent can speak a pre_call_message while the call runs. Response contract: {"status": "ok" | "confirm" | "reject", "part": "Gasket 50mm", "say": "short Hinglish sentence"}. Agent speaks say and obeys status: ok goes to read-back, confirm re-asks digit by digit, reject re-asks part/unit. get_stock(session_id, part_alias) is the same pattern (Tier 2 voice stock query).

Rules:

Endpoint answers well under 1 s. On timeout the agent proceeds to read-back and the after-call guardrail holds the entry as needs_review. Live validation improves accuracy; it is never the only defence.
Authenticate with the api_token Bearer value. Do not rely on IP allowlists (tool-call source IPs undocumented).
Correlation: pass session_id in user_data, reference it in the prompt ({{session_id}}); the LLM fills it as a parameter.
Placement inside agent_config via API is inferred (from the documented transfer_call pattern under tools_config.api_tools.tools + tools_params). Verify once: create the tool in the dashboard, read the agent back via API, copy its JSON into agent.json. (The create-agent OpenAPI in the PDFs only schema-defines transfer_call under api_tools.)

6. Watchtower (rules-based, every score shows components)

Runs after every confirmed event and on a schedule. Hinglish number handling lives in the parser/guardrails, not in the Watchtower.

Signals: slack days (shortage engine); supplier slip (on-time rate, avg slip days, last 5 POs, min 3 needed); single-source exposure; data confidence (no confirmed count for 7+ days, or >30% reconcile mismatches); machine reliability (3+ incidents in 7 days); unacked handover items; owner notes (delay days for named suppliers, with expiry). External feeds (weather/news/commodity) are not built and not verified; signals.py is the plug-in point.

Math

effective_eta(PO)      = eta_date + avg_slip_days(supplier) + owner_note_delay_days

effective_lead(part)   = lead_time_days + avg_slip_days(supplier) + owner_note_delay_days

first_short_date(part) = first date where projected stock < 0

slack_days(part)       = (first_short_date - today) - effective_lead(part)   # no PO covers it

                         need_date - effective_eta(PO)                       # PO exists, may be late

projected(part, d)     = on_hand + sum(PO qty with effective_eta <= d)

                         - sum(WO qty x qty_per_unit with start_date <= d)

Work orders consume on start_date (conservative).

Bands: Red >= 50, Amber 25-49, Green < 25. Red: top of list + in the Open brief (top 3) + supplier ETA call if PO open (Tier 2). Amber: listed; next brief only if <3 Reds; Close call asks for a fresh count. Green: collapsed, silent.

Lanes added in v3

Capital (over-stock): (on_hand + open PO qty) / max(avg_daily_use, planned_daily_use) > 60 days flags "Over" with money tied up (needs optional unit_cost). Needs 14+ days of usage, else "insufficient data". Action: "defer this PO". 60 is a starting setting.
Reorder suggestion: suggested_qty = max(0, avg_daily_use x (effective_lead + safety_days) - (on_hand + open_PO)) + planned_WO_shortfall, safety_days default 2. Suggestion only, never an automatic order.
Supplier scorecard: on-time rate, avg slip, lead-time drift vs master, last 5 POs.

9.1 Gotchas that break generated code

POST /v2/agent returns 201 {agent_id, state:"created", version_id} (field is state, not status). Body must be wrapped {"agent_config": {...}, "agent_prompts": {"task_1": {"system_prompt": "..."}}}. v1 /agent returns 200 and is the old path; use v2.
POST /batches returns 201, multipart/form-data with agent_id + CSV file. POST /batches/{id}/schedule returns 200.
scheduled_at must use +00:00, never Z (Z causes 500). Must be >= 2 min in the future; Bolna rounds up to the next 10-minute mark. (Batch scheduling only; not needed for the today plan.)
Wait for completed, not call-disconnected. At disconnect, conversation_duration, total_cost, recording_url, extracted_data are null/0. completed arrives a few seconds later.
toolchain.pipelines is an array of arrays: [["transcriber","llm","synthesizer"]].
GET /batches/{id}/executions returns a bare array.
from_phone_number is optional on POST /call (account default used). Agents on telephony trunk must pass a trunk number.
Webhooks come from 13.203.39.153, 13.126.9.249, 13.202.133.53. Allow all three if firewalled.
GPT-5-series models require "temperature": 1 (400 For GPT-5 models, temperature must be 1); the field defaults to 0.1. gpt-4.1-mini with temperature 0.2 is accepted per the docs' LLM list.
LLM provider/model is not validated at creation; a wrong value only fails when a call runs. Transcriber/synthesizer/telephony providers are validated (400 Invalid value for provider).
Transcriber model + language validated as a pair; language is a plain ISO 639-1 code ("hi", never "hi-IN", even for Sarvam).
Synthesizer provider_config.language is required for cartesia, sarvam, smallest, rime, azuretts, gemini, soniox, polly; not accepted by elevenlabs, deepgram, openai; optional on maya, kalpa.
Transcriber keywords accept word:boost but the boost is stripped at save time; terms still apply (Deepgram sends as keyterm on nova-3; Sarvam reads on saaras:v4 only).
The update endpoint: AGENTS.md shows PATCH /v2/agent/{agent_id} with {"agent_config": {...}}. The older cheatsheet listed PUT. Which one to use for full updates is not confirmed in the PDFs; check the update-agent API page.
The cheatsheet listed a webhook task type, but the Create-agent OpenAPI enum for task_type is only conversation, extraction, summarization. Treat webhook as not verified.

9.6 Webhooks

Set webhook_url inside agent_config (or dashboard → agent → Extractions tab → Webhook Configuration; can limit "Trigger on statuses", add custom headers, "Send test" posts a sample completed payload). Endpoint must be public HTTPS and answer 200 quickly. Bolna POSTs on each status change (scheduled → queued → in-progress → completed, plus call-disconnected). Payload = Get-Execution response shape. Pre-call webhooks: if a tool sets pre_call_webhook_param without its own pre_call_webhook_url, it posts to the agent-level URL with status in-progress and extra fields; distinguish by status/fields. Delivery health is visible in dashboard Analytics → Webhook delivery (failed deliveries downloadable as CSV).

10. Voice prompt skeleton (use for every agent)

Role + who you serve → AI disclosure in the first line (and "call is recorded") → goal of the call in one sentence → conversation steps as a short numbered flow → rules (1-2 sentences per turn, one question at a time, read back numbers, mirror the caller's language, Hinglish OK) → what to do on silence, on confusion (max 2 re-asks), on abuse, on "talk to a human" → hard limits (never promise or say X; no OTP/card/Aadhaar/bank details, no wages, no price negotiation) → how to end the call and what summary data to capture (fixed-format confirmation line so the deterministic parser can read it).

Extra rules for Karkhana agents: at most 5 items per Close call; read numbers back as words and digits for 15/50-type ambiguity; nothing is confirmed until the caller says yes to the read-back; if the tool returns status:"confirm" re-ask digit by digit; if the tool times out, proceed to read-back (after-call guardrail will hold the entry as needs_review).

Default agent stack (flat-rate): Deepgram nova-3 (language set explicitly), gpt-4.1-mini (temp 0.2, max_tokens 150), ElevenLabs eleven_turbo_v2_5, telephony plivo. A/B once: Sarvam saaras:v4 for Hinglish accuracy (off the snapshot list; measure accuracy and the cost line).

12. Platform layer, security, compliance (design; build only what fits)

Reliability: stuck-call reconciler (any call not terminal after 10 min → poll GET /executions/{id}); retries (missed Close call retried up to 2 times inside call_window, then flagged); voicemail-detected calls write nothing and retry; idempotency (one row per execution_id); manual override in the Control Room (source = manual, audit_log).

Observability/cost: per-call cost rolled up per person/agent/org (the cost-per-factory-month number); completion, retry and voicemail rates; average length; structured logs keyed by execution_id with PII redacted.

Security: webhook source-IP allowlist (three IPs) + custom header secret set on the dashboard webhook card; tools: Bearer api_token, constant-time compare, rate limit; secrets only in env; every table carries org_id with a test proving cross-org isolation; nightly copy of the SQLite file.

Judge-mode abuse controls (F2, mandatory because the buttons dial real phones): visitor types their own number and ticks "I agree to receive this demo call"; max 2 demo calls per number per day, per-IP limit, global daily cap; daytime window via calling_guardrails; kill-switch pauses demo calls if wallet < floor (read via GET /user/me); no OTP/card/ID ever requested by voice.

Compliance (not legal advice; lawyer review before commercial launch):

Consent first (opted_in, consent_at, consent_method); suppliers opted in individually; agent says it's an AI in the first line and that the call is recorded and why.
DPDP: Rules notified Nov 2025; core duties reported to start mid-May 2027 (sources say 13 or 14 May). Voices are personal data. Design now for plain-language consent notice, purpose limitation, easy withdrawal, grievance contact, retention setting (docs/CONSENT.md).
Retention hypothesis: raw transcripts/recordings 90 days, then only structured events. Deletion on request, logged.
No sensitive data by voice; no wages/pay computation; human handoff on every call (logged handoff_requested); no lock-in (CSV export).
Telecom rules for commercial calling: not researched.
